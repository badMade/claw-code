## 2024-04-09 - Rust String Cloning Optimization
**Learning:** In Rust, building lists of string parts for joining (e.g., `vec![string1.clone(), string2.clone()].join(" ")`) is a common pattern that can lead to unnecessary heap allocations. This codebase frequently does this when formatting reports. When the source values are already `String`s, borrowing them as `&str` and pushing them to a `Vec<&str>` before calling `.join()` entirely avoids these intermediate heap allocations. Additionally, calling `.to_string()` on static string slices just to appease a `Vec<String>` is wasteful when `Vec<&str>` works perfectly.
**Action:** When constructing strings from parts using `Vec` and `.join()`, look for opportunities to use a `Vec<&str>` populated with borrowed string slices (`.as_str()`) instead of a `Vec<String>` populated with cloned strings (`.clone()`).

## $(date +%Y-%m-%d) - Optimization of O(N) tuple lookups with cached_property mappings
* **Pattern**: Replacing linear O(N) array/tuple iteration with lazily-evaluated O(1) dictionary lookups.
* **Learning**: When accessing elements in a static/frozen list via a string identifier (e.g., `command(name: str)` looking through `self.commands`), performance degrades linearly as the list grows, and frequent calls cause excessive string allocations (e.g., `name.lower()` inside loops). This can be mitigated by generating a lookup dictionary mapping the identifier to the object.
* **Implementation Details**: Using `@functools.cached_property` inside a `dataclass(frozen=True)` is fully supported in Python 3.12+ without `FrozenInstanceError` (as it bypasses `__setattr__` using direct `__dict__` manipulation). By iterating over the collection *once* upon property access and checking `if lowered not in lookup`, we guarantee O(1) subsequent lookup times and preserve the original first-match priority of the array iteration. In this repository, `ExecutionRegistry.command` and `.tool` lookups were improved from O(N) taking ~6.34s per 100k iterations to O(1) taking ~0.25s.
